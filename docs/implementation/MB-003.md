# MB-003 — Consistent common app states

Status: implemented  
Phase: P0  
Parent: MB-E01 Foundation

## Acceptance evidence

### Accessible common-state components

`src/design-system/common-state.tsx` provides one typed component for loading,
empty, error, offline, stale, and partial states. It supports panel and inline
presentation, optional freshness metadata, and accessible recovery actions.
Loading uses static layout-preserving placeholders without fake money values.
Errors use an assertive alert; all other changes use polite announcements.

The old state notice was removed from `feedback.tsx`, which now owns only progress
feedback. This keeps a single authoritative definition of app-state kinds and
presentation.

### Demonstration fixtures

`SYNTHETIC_COMMON_APP_STATES` demonstrates every state exactly once. The About
screen links to `/state-preview`, where the fixtures render through the reusable
feature screen. The route injects fixtures at the composition boundary so the
feature does not depend on the test-fixture layer.

### Goals integration

The Goals feature uses `CommonState` for every non-ready state. Error and offline
states can retry; stale and partial states can refresh. Cached cards remain visible
offline, usable cards remain visible for stale/partial results, and cached or stale
results show a deterministic last-updated label. Replaced or unmounted requests
cannot update the screen.

The local repository contract now supports optional `cachedAt`. The synthetic
adapter can deterministically produce fresh, stale, partial, offline, and error
results without changing feature code.

## Shared completion review

- Component tests cover every kind, roles, live regions, busy state, independent
  actions, 44-point target height, disabled actions, and metadata.
- Fixture tests prove complete state coverage, synthetic identifiers, freshness,
  and loading copy without placeholder financial values.
- Preview tests prove all fixtures render and actions remain local and observable.
- Goals tests cover loading, empty, error, offline with and without cache, stale,
  partial, ready, freshness, retry, safe rejection copy, and accessible progress.
- Repository, use-case, presenter, route-composition, navigation-contract,
  architecture-boundary, and adjacent-test contracts were updated.
- Calendar uses the inline partial pattern; Journey and not-found use panel empty
  and error patterns. Ready/success intentionally has no common-state notice.
- All fixtures and examples are synthetic. No new logs, analytics, API, network
  dependency, or persisted financial data were introduced.
