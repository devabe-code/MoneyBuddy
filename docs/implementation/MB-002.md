# MB-002 — Feature and domain boundaries

Status: implemented  
Phase: P0  
Parent: MB-E01 Foundation

## Acceptance evidence

### Folder conventions documented

[Client folder and dependency conventions](../architecture/folder-conventions.md)
defines ownership, permitted dependency direction, the feature workflow, and the
steps for adding a feature. The rules are enforced by an import-boundary test and
the existing adjacent-test contract.

### Sample feature uses repository and domain interfaces

The Goals route is a composition layer. It renders `SavingsGoalsScreen` with a
loader from the Goals composition root. That loader depends on:

- `SavingsGoalRepository`, implemented by `SyntheticSavingsGoalRepository`; and
- `SavingsGoalProgressPolicy`, implemented by the deterministic default policy.

The repository returns raw domain records. The domain policy calculates progress
and remaining minor units with integer arithmetic. The feature presenter formats
the result for `GoalProgressCard`. No route or screen calculates financial values.

The repository result contract is documented in
[Savings goal repository contract](../contracts/savings-goal-repository.md).

## Shared completion review

### Tests and architecture risk

- Domain factory tests cover invalid IDs, names, targets, and saved amounts.
- Policy tests cover normal progress, exact integer rounding, and overfunded goals.
- Repository contract and adapter tests prove replaceability and freshness.
- Use-case tests cover fresh, stale, partial, empty, offline cache, and error data.
- Presenter tests cover exact minor-unit formatting without floating-point math.
- Feature rendering tests cover loading, empty, error, offline, stale, partial,
  ready, cached data, accessible progress, and safe rejection handling.
- Architecture and test-pairing tests enforce the boundaries structurally.

### Accessibility and states

The sample screen exposes loading, empty, error, offline, stale, and partial states
through the shared accessible `StateNotice`. Ready data uses labeled progress bars.
Offline cached data remains visible with a non-color notice. Unexpected adapter
errors are replaced with safe user-facing copy.

### Synthetic-data policy

All adapter, fixture, screen, and test values use synthetic IDs and amounts. No
repository layer logs values or identifiers.

### API impact

No network API is added. The local repository port is documented now so future
local or HTTP adapters can be introduced without changing feature or domain code.
